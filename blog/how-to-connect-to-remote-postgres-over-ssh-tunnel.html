How to Connect to Remote PostgreSQL Over SSH Tunnel (Step-by-Step 2026 Guide)

Published: November 2026 • 10 min read • By SSH Desktop Engineering Team

PostgreSQL is the world's most advanced open-source relational database. But when you deploy PostgreSQL on a production Linux server, DigitalOcean Droplet, AWS EC2, or Hetzner VPS, how do you safely connect your local development tools (pgAdmin, DBeaver, psql, VS Code) to manage it?

The naive approach is binding PostgreSQL to 0.0.0.0 and opening port 5432 in your firewall. Never do this in production.

In this guide, you will learn why exposing PostgreSQL to the public web is hazardous, how an SSH tunnel provides military-grade security without opening any firewall ports, and how to establish the tunnel using CLI commands, GUI database clients, and SSH Desktop's visual database studio.

Why You Must Never Expose PostgreSQL Port 5432 Publicly

Within seconds of opening port 5432 on a public IP address, automated port scanners (Shodan, Censys, botnets) will discover your server and flood it with dictionary attacks against the postgres superuser role.

Security Risks of Public Database Ports:
  • Credential Brute-Forcing: Relentless bot authentication requests exhaust database connections and spike CPU usage.
  • Zero-Day Protocol Vulnerabilities: Any unpatched flaw in PostgreSQL's network protocol (like CVE-2021-32027) can lead to arbitrary remote code execution.
  • Data Exfiltration over Unencrypted Connections: If SSL/TLS is improperly configured or unverified, database queries and sensitive passwords travel in plaintext across the internet.
  • Compliance Failures: Exposing database management ports violates PCI-DSS Requirement 1.3, HIPAA Security Rule §164.312, and SOC 2 Type II trust criteria.

By keeping PostgreSQL bound strictly to 127.0.0.1 (localhost) on the server, the database cannot be reached from the outside world. All communication is routed through an encrypted SSH tunnel over port 22.

How an SSH Tunnel for PostgreSQL Works

An SSH local port forwarding tunnel (-L) acts as a secure cryptographic pipe:

  1. Your SSH client opens a local listening port (e.g. localhost:5432) on your laptop.
  2. When your local database tool (pgAdmin, DBeaver, or code) connects to localhost:5432, the SSH client intercepts the TCP packets.
  3. The SSH client encrypts the packets and transports them over the existing SSH connection (port 22) to the remote server.
  4. The remote SSH daemon decrypts the packets and passes them locally to 127.0.0.1:5432 on the database server.
  5. Query results travel back through the exact same encrypted pipeline.

Method 1: Terminal CLI (OpenSSH Local Port Forwarding)

Open your terminal (macOS/Linux Terminal or Windows Terminal with PowerShell) and run:

ssh -N -L 5432:localhost:5432 user@your-server-ip

Flag Breakdown:

  • -N: Tells OpenSSH not to execute a remote shell. It instructs SSH to only forward ports, which conserves bandwidth and system resources.
  • -L [local_port]:[remote_target]:[remote_target_port]: Specifies local port forwarding.
    • 5432 (first number): The port opened on your local laptop.
    • localhost: The address the remote server will connect to (from the server's perspective).
    • 5432 (second number): The remote PostgreSQL port.
  • user@your-server-ip: Your remote server SSH user and IP address.

Handling Local Port Conflicts (Port 5432 Already in Use):

If you already have a local PostgreSQL server running for local development (e.g., via Docker or Homebrew), trying to bind port 5432 will trigger:

bind [127.0.0.1]:5432: Address already in use
channel_setup_fwd_listener_tcpip: cannot listen to port: 5432
Could not request local forwarding.

The fix is simple: change the local port to 5433:

ssh -N -L 5433:localhost:5432 user@your-server-ip

Now point your database client to localhost:5433 instead of 5432.

Testing Connection with psql:

Open a second terminal window and test the tunnel:

psql -h localhost -p 5432 -U postgres -d your_db_name

Method 2: Configuring Database Clients Directly

If you prefer your database client to manage the SSH tunnel lifecycle automatically whenever you open the connection, configure it inside the tool:

1. DBeaver:

  1. Click New Database Connection → Select PostgreSQL.
  2. In the Main tab:
    • Host: localhost (or 127.0.0.1)
    • Port: 5432
    • Database: your database name
    • Authentication: database username and password
  3. Switch to the SSH tab and check Use SSH Tunnel:
    • Host / IP: Your remote server's public IP address
    • Port: 22
    • User Name: Linux user (e.g., ubuntu or root)
    • Authentication Method: Public Key
    • Private Key: Browse to ~/.ssh/id_ed25519
  4. Click Test Connection. DBeaver will automatically establish the tunnel, authenticate, and list your tables!

2. pgAdmin 4:

  1. Right-click Servers → Register → Server...
  2. In the General tab, give your server a name (e.g. "Production DB").
  3. In the Connection tab:
    • Host name / address: localhost (or internal IP)
    • Port: 5432
    • Maintenance database: postgres or your app DB
    • Username: database user
  4. In the SSH Tunneling tab:
    • Toggle Use SSH tunneling to Yes.
    • Tunnel host: Your server's public IP
    • Tunnel port: 22
    • Username: your Linux SSH username
    • Authentication: Identity file
    • Identity file: select your private key
  5. Click Save.

Method 3: Private Subnet & AWS RDS Bastion Jump Host

In enterprise cloud environments (AWS, GCP, Azure, DigitalOcean), managed database instances (such as AWS RDS PostgreSQL or Google Cloud SQL) do not have public IP addresses. They reside inside an isolated Private Subnet with internal DNS names like mydb.c8x9abc.us-east-1.rds.amazonaws.com.

To access the database from your laptop, you route traffic through an EC2 instance acting as a Bastion / Jump Host residing in the VPC's Public Subnet:

# Local Tunnel through Bastion to AWS RDS:
ssh -N -L 5432:mydb.c8x9abc.us-east-1.rds.amazonaws.com:5432 ubuntu@bastion-public-ip -i ~/.ssh/bastion_key.pem

Here, OpenSSH forwards packets from your laptop to the bastion host, which then routes them over the high-speed internal AWS VPC network directly to the RDS PostgreSQL instance. Your RDS database remains 100% invisible to the outside internet.

Method 4: Automating Persistent Tunnels via SSH Config

Instead of memorizing long flags every morning, add a persistent alias in your local ~/.ssh/config file:

Host db-tunnel
HostName 198.51.100.25
User ubuntu
IdentityFile ~/.ssh/id_ed25519
LocalForward 5432 127.0.0.1:5432
ServerAliveInterval 60
ServerAliveCountMax 3
ExitOnForwardFailure yes

Now whenever you need the tunnel, just run:

ssh -N db-tunnel

The ServerAliveInterval 60 directive sends keepalive pings every 60 seconds, preventing firewalls and NAT gateways from silently dropping idle database connections.
