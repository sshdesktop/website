How to Fix 502 Bad Gateway & 504 Gateway Timeout in Nginx (2026 Guide)

Troubleshooting By SSH Desktop Engineering Team • Updated November 2026 • 10 min read

Few HTTP error codes cause more developer panic than 502 Bad Gateway. Unlike a 500 Internal Server Error, which originates within your application code, a 502 error means that Nginx—acting as your edge reverse proxy—attempted to communicate with your backend application (Node.js, Python Gunicorn, PHP-FPM, or Docker container) and received an invalid response, connection refusal, or abrupt socket closure.

Executive Summary

Diagnosing a 502 error requires checking three points of failure: (1) Is the upstream application process alive? (2) Is Nginx pointing to the exact listening port or UNIX socket? (3) Are there file permission mismatches on socket files? In this guide, we provide a step-by-step diagnostic playbook and visual troubleshooting via SSH Desktop Log Analysis and Process Manager.

1. The 4 Most Common Causes of 502 Bad Gateway

Error Log Message Underlying Root Cause Resolution
connect() failed (111: Connection refused) Upstream service (Node.js/Python/Go) is stopped or crashed Restart backend service with systemctl or pm2
connect() failed (13: Permission denied) Nginx (www-data) cannot read the PHP-FPM/Gunicorn UNIX socket file Fix socket ownership with chown www-data:www-data
upstream prematurely closed connection Backend process ran out of memory (OOM) or crashed mid-request Inspect app crash logs and increase worker memory limits
no live upstreams while connecting to upstream All servers in an upstream load balancing pool failed health checks Verify backend server addresses and network firewalls

2. Step-by-Step Diagnostic Playbook

Step 1: Inspect the Nginx Error Log

The error log reveals the exact reason Nginx failed to reach the upstream: 

sudo tail -n 50 /var/log/nginx/error.log

Step 2: Check If the Upstream Application is Alive

# Check systemd service status:
sudo systemctl status myapp.service
# Or if using PHP-FPM:
sudo systemctl status php8.3-fpm

# Verify the application is listening on the expected port (e.g. 3000):
sudo ss -tulpn | grep 3000

Step 3: Test Upstream Directly on Localhost

Bypass Nginx completely by issuing a direct curl request to your application: 

curl -I http://127.0.0.1:3000/
# If curl outputs "Connection refused", your app is not running!

Step 4: Fixing UNIX Socket Permission Denied

If your Nginx error log reports "Permission denied" while reading a UNIX domain socket (e.g. /run/php/php8.3-fpm.sock): 

# Check socket owner:
ls -l /run/php/php8.3-fpm.sock

# Ensure Nginx user (www-data or nginx) owns the socket:
sudo chown www-data:www-data /run/php/php8.3-fpm.sock
sudo chmod 660 /run/php/php8.3-fpm.sock

3. How to Fix 504 Gateway Timeout

A 504 error means your backend accepted the connection, but took longer than Nginx's 60-second default timeout to return HTTP response headers (e.g., long-running database reports, slow API imports). 

location / {
    proxy_pass http://127.0.0.1:3000;
    
    # Increase proxy timeout thresholds to 300 seconds:
    proxy_connect_timeout 300s;
    proxy_send_timeout 300s;
    proxy_read_timeout 300s;
}

4. Frequently Asked Questions

What is the difference between 502 Bad Gateway and 504 Gateway Timeout?

A 502 Bad Gateway indicates that Nginx attempted to connect to the upstream backend (such as Node.js or PHP-FPM) and received an immediate invalid response, connection refused, or connection reset (the backend service is crashed, stopped, or not listening). A 504 Gateway Timeout means Nginx connected successfully, but the upstream application took longer to respond than the configured proxy_read_timeout (the backend is alive but frozen or bogged down by slow queries).

How do I check Nginx error logs in real time?

Execute sudo tail -f /var/log/nginx/error.log in your terminal or use SSH Desktop's visual Log Streamer. Look for lines containing connect() failed (111: Connection refused) or upstream prematurely closed connection.

How do I increase the gateway timeout limit in Nginx?

Inside your location or http block, increase timeout limits: proxy_connect_timeout 300s;, proxy_send_timeout 300s;, and proxy_read_timeout 300s;. Then reload Nginx with sudo systemctl reload nginx.
