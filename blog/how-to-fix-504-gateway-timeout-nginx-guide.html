How to Fix 504 Gateway Timeout Error in Nginx: Step-by-Step Guide (2026)

Nothing frustrates users more than staring at a blank screen for a minute only to encounter 504 Gateway Time-out. Unlike 502 errors where backends crash outright, 504 errors mean your application is bogged down by unindexed database queries, external API deadlocks, or long-running computations exceeding reverse proxy limits. Learn the step-by-step troubleshooting playbook to diagnose and eliminate 504 errors in 2026.

How Nginx Handles Upstream Timers

By default, Nginx maintains a strict 60-second response window (proxy_read_timeout 60s; or fastcgi_read_timeout 60s;). If an upstream process takes 60.01 seconds to generate an HTTP response header, Nginx closes the client socket and returns a 504 status code.

Step 1: Inspect Nginx Error Logs

Check the exact error message in /var/log/nginx/error.log:

sudo tail -n 50 -f /var/log/nginx/error.log | grep -E '(upstream timed out|504)'

You will typically see:

[error] 1450#1450: *284 upstream timed out (110: Connection timed out) while reading response header from upstream, client: 203.0.113.19, server: example.com, request: "POST /reports/export HTTP/2.0", upstream: "fastcgi://unix:/var/run/php/php8.3-fpm.sock:"

Step 2: Increase Timeout Directives for Reverse Proxies (Node / Python / Go)

If your upstream application is Node.js, Python Gunicorn, or Docker, increase proxy timeouts in your server block:

location / {
    proxy_pass http://localhost:3000;
    include proxy_params;

    # Increase timeout limits to 300 seconds
    proxy_connect_timeout 300s;
    proxy_send_timeout    300s;
    proxy_read_timeout    300s;
    send_timeout          300s;
}

Step 3: Fix 504 Errors on PHP-FPM / WordPress

For PHP-FPM, you must tune both Nginx and PHP runtime configurations:

1. In Nginx (/etc/nginx/sites-available/example.com):

location ~ \.php$ {
    include snippets/fastcgi-php.conf;
    fastcgi_pass unix:/var/run/php/php8.3-fpm.sock;

    # Increase FastCGI timeout
    fastcgi_read_timeout 300s;
}

2. In php.ini (/etc/php/8.3/fpm/php.ini):

max_execution_time = 300

3. In the PHP-FPM pool (/etc/php/8.3/fpm/pool.d/www.conf):

request_terminate_timeout = 300s

Reload both services:

sudo systemctl reload php8.3-fpm
sudo systemctl reload nginx

Step 4: Troubleshoot the Underlying Cause (Slow Queries & Locks)

Increasing timeouts is often a temporary band-aid. The underlying issue is usually database lock contention or unindexed table scans:

  • PostgreSQL: Run SELECT pid, now() - query_start AS duration, query FROM pg_stat_activity WHERE state != 'idle' ORDER BY duration DESC; to spot frozen transactions.
  • MySQL: Run SHOW FULL PROCESSLIST; to find slow queries holding table metadata locks.
  • Third-Party APIs: Ensure outgoing HTTP requests have explicit connection and read timeouts configured in application code.

Frequently Asked Questions

What is the root cause of an HTTP 504 Gateway Timeout in Nginx?

A 504 Gateway Timeout means Nginx successfully connected to your upstream backend (PHP-FPM, Node.js, Python Gunicorn, or an internal microservice), but the upstream took longer to send a response than the configured timeout limit (default 60 seconds). It is caused by slow database queries, long-running batch jobs, or thread pool exhaustion.

What is the difference between 502 Bad Gateway and 504 Gateway Timeout?

A 502 Bad Gateway means the upstream backend crashed, refused the connection, or closed the socket immediately (not running). A 504 Gateway Timeout means the upstream backend is alive and accepted the connection, but froze or timed out before delivering the response (too slow).

Which timeout directives in Nginx resolve 504 errors?

For reverse proxy setups (Node, Python, Go): proxy_connect_timeout 300s;, proxy_send_timeout 300s;, and proxy_read_timeout 300s;. For FastCGI (PHP-FPM): fastcgi_read_timeout 300s; alongside request_terminate_timeout in php-fpm.conf.
