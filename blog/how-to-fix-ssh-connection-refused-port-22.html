How to Fix 'SSH Connection Refused' on Port 22: 7 Proven Solutions (2026 Guide)

Published: November 2026 • 10 min read • By SSH Desktop Engineering Team

You attempt to connect to your Linux server, VPS, Raspberry Pi, or cloud virtual machine, but your terminal immediately throws:

ssh: connect to host 198.51.100.42 port 22: Connection refused

Unlike an Operation timed out error (which means packets are disappearing into a black hole before reaching the server), a Connection refused error is definitive: your network packets successfully reached the destination IP, but nothing on that server is listening on port 22, or the server's operating system explicitly rejected the TCP connection.

Whether you are running Ubuntu, Debian, CentOS, AlmaLinux, Arch, or a cloud instance on AWS EC2, DigitalOcean, or Hetzner, this step-by-step guide will help you isolate and fix the root cause in minutes.

Step 0: Test Port Availability from Your Client (Netcat & Nmap)

Before modifying server settings, check if port 22 is open, closed, or filtered from your local machine:

# Using netcat (macOS / Linux):
nc -zv 198.51.100.42 22

# Using PowerShell (Windows 11 / 10):
Test-NetConnection -ComputerName 198.51.100.42 -Port 22

If TcpTestSucceeded : False or netcat reports Connection refused, proceed through the 7 solutions below.

Solution 1: Check If the SSH Daemon (sshd) Is Running

The most frequent cause is simply that the OpenSSH server process has crashed, stopped, or was never enabled on boot.

Access your server via your cloud provider's web console (e.g., AWS EC2 Serial Console, DigitalOcean Droplet Console, Linode Lish, or VNC) and check the service status:

# On Ubuntu, Debian, and Linux Mint:
sudo systemctl status ssh

# On CentOS, RHEL, Fedora, and AlmaLinux:
sudo systemctl status sshd

If the output shows Active: inactive (dead) or failed, start and enable the daemon:

sudo systemctl enable --now ssh # Ubuntu/Debian
sudo systemctl enable --now sshd # RHEL/CentOS

Verify the service is actively listening on a TCP port:

sudo ss -tulpn | grep -i ssh

You should see an active listener on 0.0.0.0:22 or :::22.

Solution 2: Install OpenSSH Server (If Not Present)

Minimal Linux container images, desktop distributions, and fresh minimal server installs often omit the SSH server package by default.

Install OpenSSH server using your distribution's package manager:

# Ubuntu / Debian:
sudo apt update && sudo apt install -y openssh-server

# CentOS / RHEL / AlmaLinux:
sudo dnf install -y openssh-server

# Arch Linux:
sudo pacman -S openssh

Once installed, enable and start the service:

sudo systemctl enable --now ssh

Solution 3: Unblock Port 22 in Host Firewalls (UFW & firewalld)

Even when sshd is running, local host firewalls like UFW (Uncomplicated Firewall) or firewalld may be actively rejecting incoming packets on port 22.

Fix for Ubuntu & Debian (UFW):

Check UFW status:

sudo ufw status verbose

If UFW is active and port 22 is missing, open it:

sudo ufw allow 22/tcp comment 'Allow OpenSSH'
sudo ufw reload

Fix for CentOS, RHEL, and Fedora (firewalld):

Check firewalld status and open the SSH service:

sudo firewall-cmd --state
sudo firewall-cmd --permanent --add-service=ssh
sudo firewall-cmd --reload

Raw iptables / nftables:

If your server uses raw iptables rules, ensure incoming traffic on port 22 is accepted:

sudo iptables -A INPUT -p tcp --dport 22 -j ACCEPT
sudo netfilter-persistent save # on Debian/Ubuntu

Solution 4: Verify SSH Is Not Listening on a Custom Port

Security best practices frequently involve changing the default SSH port from 22 to an alternate port (such as 2222 or 49152) to reduce botnet scanning noise.

If someone modified /etc/ssh/sshd_config, connecting to port 22 will immediately return Connection refused!

Check the active port configuration in sshd_config:

grep -E "^Port" /etc/ssh/sshd_config /etc/ssh/sshd_config.d/*.conf 2>/dev/null

If the output shows Port 2222, specify the custom port with the -p flag when connecting:

ssh -p 2222 user@198.51.100.42
Tip for SSH Desktop Users: In SSH Desktop, you can save custom ports per server, auto-detect listening ports on local subnets, and bookmark sessions with visual health indicators.

Solution 5: AWS EC2, GCP, & Cloud Security Groups

In cloud environments (Amazon Web Services, Google Cloud Platform, Microsoft Azure, DigitalOcean), servers are protected by an external Cloud Security Group / VPC Firewall that operates outside the Linux operating system.

AWS EC2 Security Group Checklist:

  1. Open the AWS Management Console → EC2 → Instances.
  2. Select your EC2 instance and switch to the Security tab.
  3. Click on the active Security Group.
  4. In Inbound rules, verify there is an entry:
    • Type: SSH
    • Protocol: TCP
    • Port range: 22
    • Source: My IP (e.g. 203.0.113.10/32) or 0.0.0.0/0
  5. If missing, click Edit inbound rules → Add rule → Save rules.

Solution 6: Check for IP Address & DNS Collisions

Are you sure you are connecting to the intended machine?

  • DHCP IP Reassignment: If connecting to a local server or Raspberry Pi on your home/office network, the router's DHCP lease may have expired, assigning the old IP (e.g. 192.168.1.105) to a smart TV, printer, or phone that refuses port 22.
  • Stale DNS Records: If using a domain like server.example.com, run dig +short server.example.com or nslookup server.example.com to verify the record points to the current server public IP.

Solution 7: Solve Systemd Socket Activation (Ubuntu 22.10+)

Starting in Ubuntu 22.10 and continued in Ubuntu 24.04 LTS, Ubuntu transitioned OpenSSH to systemd socket-based activation. The traditional ssh.service is managed by ssh.socket.

If ssh.socket is disabled, connections will fail with Connection refused even if sshd is installed!

Verify socket activation:

sudo systemctl status ssh.socket
sudo systemctl enable --now ssh.socket
