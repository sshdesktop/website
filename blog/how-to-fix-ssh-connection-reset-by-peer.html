How to Fix 'Connection Reset by Peer' in SSH: 2026 Guide

Few errors are as disruptive as kex_exchange_identification: read: Connection reset by peer or having an active shell suddenly terminate with Connection to 198.51.100.24 closed by remote host. Unlike a connection refusal (which occurs before the TCP handshake completes), a connection reset means the TCP handshake succeeded, but either the remote server or an intermediate firewall abruptly aborted the session. Learn how to diagnose and resolve SSH connection resets in 2026.

The Root Causes of TCP RST in SSH

  • Firewall or NAT State Timeouts: Cloud security groups, stateful NAT gateways, and home routers silently drop idle connections after a timeout window. When you next type a command, the gateway returns a TCP RST.
  • sshd MaxStartups Limits: When burst connections occur from automated deployment pipelines or multiple team members, OpenSSH drops excess unauthenticated connections.
  • Fail2ban or IP Rate Limiting: A background script or IDE plugin with bad credentials triggers Fail2ban to insert a drop rule mid-session.
  • MTU / Packet Fragmentation: Path MTU Discovery (PMTU) blackholes drop large packets during public key exchange or high-throughput file transfers.

Step 1: Diagnose with Verbose Client Logging

Run SSH with maximum verbosity (-vvv) to determine the exact handshake step where the connection terminates:

ssh -vvv user@server.example.com

If the reset occurs immediately after SSH2_MSG_KEXINIT, the issue is typically MTU fragmentation or IP filtering. If it occurs after authentication during shell startup, it is typically a PAM session or shell configuration crash.

Step 2: Enable TCP Keepalive Heartbeats

Prevent firewalls and NAT gateways from dropping idle sessions by configuring client keepalives in ~/.ssh/config: 

Host *
    ServerAliveInterval 60
    ServerAliveCountMax 3
    TCPKeepAlive yes
    IPQoS throughput

On the server side, edit /etc/ssh/sshd_config to ensure the daemon also maintains session health: 

ClientAliveInterval 60
ClientAliveCountMax 3
sudo systemctl reload sshd

Step 3: Tune MaxStartups and MaxSessions in sshd

If your server handles frequent CI/CD jobs, SFTP transfers, or multiple concurrent developers, increase the concurrency ceiling in /etc/ssh/sshd_config: 

# Format: start:rate:full
# Start dropping at 50 connections, drop 30% linearly, drop 100% at 200
MaxStartups 50:30:200

# Increase maximum concurrent open sessions per network connection
MaxSessions 50
sudo sshd -t && sudo systemctl reload sshd

Step 4: Check Fail2ban and UFW Firewall Rules

Verify if your client IP address was banned by Fail2ban:

# Check fail2ban SSH jail status
sudo fail2ban-client status sshd

# Unban your client IP if present
sudo fail2ban-client set sshd unbanip 203.0.113.45

Whitelist your office or home static IP in /etc/fail2ban/jail.local:

[DEFAULT]
ignoreip = 127.0.0.1/8 ::1 203.0.113.45/32

Step 5: Fix Path MTU (Maximum Transmission Unit) Mismatches

If resets happen over VPNs, WireGuard tunnels, or PPPoE connections when transmitting large blocks of text, test your connection MTU: 

# Ping with Don't Fragment (DF) flag set
ping -M do -s 1472 server.example.com

If ping packets drop, reduce your client network interface MTU to 1420 or 1380: 

# Linux interface MTU adjustment
sudo ip link set dev eth0 mtu 1400

Frequently Asked Questions

What causes 'Connection reset by peer' during an SSH session?

The error indicates that the remote server, intermediate firewall, or NAT router abruptly sent a TCP RST (Reset) packet to tear down the connection. Common causes include SSH MaxStartups concurrency limits, firewall state table timeouts terminating idle sessions, fail2ban banning the client IP mid-session, or MTU packet fragmentation issues.

How do SSH keepalive directives prevent connection resets?

Firewalls and NAT gateways drop idle TCP states after 5 to 15 minutes of silence. Setting ServerAliveInterval 60 in your client configuration sends an encrypted heartbeat packet every 60 seconds, keeping stateful firewall translation tables open indefinitely.

How does sshd MaxStartups cause random connection drops under heavy load?

The sshd daemon limits unauthenticated concurrent connections to prevent DoS attacks (defaulting to 10:30:100). If automated CI/CD runners or multiple developers connect simultaneously, incoming connections exceeding this threshold are immediately rejected with a TCP RST.
