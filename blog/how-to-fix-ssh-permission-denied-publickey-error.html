How to Fix 'Permission Denied (publickey)' in SSH: 5 Causes & Solutions (2026 Guide)

Published: November 2026 • 11 min read • By SSH Desktop Engineering Team

You open your terminal, type ssh user@your-server-ip, press Enter, and are immediately greeted with this dreaded failure:

user@your-server-ip: Permission denied (publickey,gssapi-keyex,gssapi-with-mic).

Or on newer Linux servers, simply:

Permission denied (publickey).

This is arguably the most common and infuriating error encountered in SSH administration. It happens on Ubuntu, Debian, CentOS, AlmaLinux, Arch, and AWS EC2 instances, and plagues users connecting from Windows 11, macOS, and Linux workstations.

In this comprehensive guide, we unpack exactly why this error occurs, how to run verbose diagnostic traces, and how to permanently fix the 5 underlying causes across both client and server machines.

Step 0: The Golden Diagnostic Command (Verbose Mode)

Before guessing and modifying random configuration files, force SSH into verbose debugging mode by adding the -vvv flag:

ssh -vvv user@your-server-ip

The output prints a full handshake trace. Scroll down and look for these tell-tale diagnostic patterns:

  • debug1: Offering public key: /Users/name/.ssh/id_ed25519 followed by debug1: Authentications that can continue: publickey: Your client sent your public key, but the remote server did not accept it.
  • debug1: send_pubkey_test: no mutual signature algorithm: The remote OpenSSH server is newer and refused your old RSA key format (SHA-1 deprecation).
  • debug1: Skipping ssh-dss key ... not in PubkeyAcceptedKeyTypes: You are using an insecure legacy key format rejected by the client or server.
  • debug1: Trying private key: ... no such file or directory: Your client is trying default key names that do not exist on your computer.
  • debug1: Disconnecting: Too many authentication failures: Your SSH agent is offering too many irrelevant keys before reaching the correct one.

Cause 1: Incorrect Permissions on Client Private Key File

OpenSSH enforces strict security standards on the client machine. If your private key (e.g., id_ed25519 or id_rsa) has read or write permissions granted to any other user or group, OpenSSH will refuse to read it and output:

@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@ WARNING: UNPROTECTED PRIVATE KEY FILE! @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
Permissions 0644 for '/home/user/.ssh/id_ed25519' are too open.
It is required that your private key files are NOT accessible by others.
This private key will be ignored.
Load key "/home/user/.ssh/id_ed25519": bad permissions
Permission denied (publickey).

Fix on Linux & macOS:

Reset permissions so that only your user account has read/write privileges:

chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519
chmod 600 ~/.ssh/id_rsa # if using RSA

Fix on Windows 11 / Windows 10 (PowerShell):

Windows uses NTFS Access Control Lists (ACLs) rather than POSIX permissions. If Windows inherited permissions from parent folders, OpenSSH will reject the key.

Open PowerShell as Administrator and run the following commands on your key file:

# 1. Navigate to your user's SSH folder
cd $env:USERPROFILE.ssh

# 2. Disable inheritance and remove inherited rules
icacls id_ed25519 /inheritance:r

# 3. Grant full read access exclusively to your current Windows username
icacls id_ed25519 /grant:r "$($env:USERNAME):(R)"

Now test connecting again: ssh user@your-server-ip.

Cause 2: Incorrect Server-Side Permissions (~/.ssh & authorized_keys)

By default, OpenSSH server enables StrictModes yes. This directive requires that the remote user's home directory, .ssh directory, and authorized_keys file are not writable by any other user or group on the server. If any parent directory is group-writable, OpenSSH silently ignores the public key!

Required Linux Server Permissions:

Directory / File Required Octal Permissions String Fix Command
Home folder (/home/username) 755 or 700 drwxr-xr-x chmod 755 /home/username
SSH folder (~/.ssh) 700 drwx------ chmod 700 ~/.ssh
Authorized keys (~/.ssh/authorized_keys) 600 -rw------- chmod 600 ~/.ssh/authorized_keys
Ownership User's UID:GID username:username chown -R $USER:$USER ~/.ssh
Crucial Trap: A common mistake is running chmod 777 ~/.ssh in an attempt to "open up access". This has the exact opposite effect! OpenSSH considers permissions 777 a critical security breach and will immediately refuse to authenticate.

Cause 3: The Public Key Is Missing or Malformed in authorized_keys

Remember the core asymmetric cryptography rule: your private key stays on your local laptop, while your public key (ending in .pub) must be appended to the server's ~/.ssh/authorized_keys file.

Common Pitfalls When Adding the Public Key:

  1. Pasting the private key instead of public: Never paste id_ed25519 into authorized_keys. Only paste the contents of id_ed25519.pub.
  2. Accidental line breaks: An SSH public key must be on exactly one single line. If your clipboard broke the key across two lines, it will fail silently.
  3. Windows CRLF carriage returns: Pasting from Notepad can inject Windows endings. Clean it up on Linux using sed -i 's/ $//' ~/.ssh/authorized_keys.

How to Properly Append Your Key:

From your local terminal, use ssh-copy-id (available on Linux, macOS, and Git Bash):

ssh-copy-id -i ~/.ssh/id_ed25519.pub user@your-server-ip

Or from Windows 11 PowerShell without ssh-copy-id:

type $env:USERPROFILE.sshid_ed25519.pub | ssh user@your-server-ip "cat >> ~/.ssh/authorized_keys"

Cause 4: OpenSSH 8.8+ Deprecated Legacy RSA (SHA-1) Keys

Did your connection suddenly start failing after upgrading your server to Ubuntu 22.04, Ubuntu 24.04, Debian 12, or Fedora?

Starting in OpenSSH 8.8, the legacy ssh-rsa signature algorithm was disabled by default because SHA-1 hash collisions are computationally viable. If you generated an RSA key years ago with standard ssh-keygen -t rsa, modern SSH servers will reject it even if the key is valid and present in authorized_keys.

The Recommended Long-Term Fix: Switch to Ed25519

Generate a high-security Ed25519 elliptical curve key pair. It is faster, shorter, and far more secure than legacy RSA:

ssh-keygen -t ed25519 -C "your_email@example.com"

Temporary Workaround (If You Must Keep Your Old RSA Key):

You can tell your local OpenSSH client to accept legacy RSA algorithms by editing your local ~/.ssh/config file:

Host your-server-ip
HostName your-server-ip
User user
PubkeyAcceptedKeyTypes +ssh-rsa
HostKeyAlgorithms +ssh-rsa

Cause 5: Too Many Authentication Failures (Agent Key Overload)

If you work with GitHub, GitLab, AWS, and multiple clients, your local SSH agent might hold 5, 10, or more loaded private keys.

By default, Linux SSH servers have MaxAuthTries 6 in /etc/ssh/sshd_config. When you initiate a connection, your client will automatically offer every key stored in ssh-agent one by one.

If your server disconnects you after trying 6 irrelevant keys before reaching the correct key for that specific server, the server will terminate the session:

Received disconnect from your-server-ip port 22:2: Too many authentication failures
Disconnected from your-server-ip port 22

Solution: Force "IdentitiesOnly"

Tell SSH to offer only the exact identity file you specify on the command line, ignoring loaded agent keys:

ssh -i ~/.ssh/id_ed25519 -o IdentitiesOnly=yes user@your-server-ip

Or save this permanently in your local ~/.ssh/config:

Host production-server
HostName 198.51.100.42
User ubuntu
IdentityFile ~/.ssh/id_production_ed25519
IdentitiesOnly yes

Cause 6: Server-Side sshd_config Disables Key Authentication

If all file permissions and keys are correct, inspect the remote SSH daemon configuration on the server:

sudo nano /etc/ssh/sshd_config

Verify the following directives:

PubkeyAuthentication yes
AuthorizedKeysFile .ssh/authorized_keys .ssh/authorized_keys2
StrictModes yes

Also check whether your username is restricted by AllowUsers or DenyUsers directives at the bottom of the file:

# If AllowUsers exists, your username MUST be listed:
AllowUsers ubuntu deployer admin

After modifying sshd_config, test syntax and restart the daemon:

sudo sshd -t
sudo systemctl restart ssh # On Ubuntu / Debian
sudo systemctl restart sshd # On CentOS / RHEL / Fedora

Troubleshooting Checklist: Client vs Server

Check Location What to Verify Standard Fix
Local Machine Private key permissions too wide chmod 600 ~/.ssh/id_* (POSIX) or icacls (Windows)
Local Machine Wrong key offered / too many keys Add -o IdentitiesOnly=yes or specify -i keyfile
Remote Server ~/.ssh directory permissions chmod 700 ~/.ssh and chown -R user:user ~/.ssh
Remote Server ~/.ssh/authorized_keys permissions chmod 600 ~/.ssh/authorized_keys
Remote Server Home directory permissions chmod 755 /home/user (never 777 or group-writable)
Remote Server sshd_config settings Ensure PubkeyAuthentication yes is enabled
