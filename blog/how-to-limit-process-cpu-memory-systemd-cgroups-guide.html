How to Limit Process CPU & Memory with Systemd Cgroups v2: 2026 Guide

A single rogue background worker, memory-leaking Node.js process, or runaway batch script can consume 100% of your server's RAM, triggering the Linux kernel OOM (Out of Memory) killer to randomly terminate essential services like sshd, nginx, or mysqld. Modern Linux distributions solve this with Control Groups v2 (cgroups v2) integrated natively into systemd. Learn how to enforce strict CPU and memory limits in 2026.

Why Legacy ulimit and nice Are Obsolete

Traditional Unix tools like ulimit and nice operate on individual PID boundaries. If an application (such as Chromium, Celery, or Node.js cluster) forks 20 child workers, each child inherits a separate limit, quickly multiplying total memory consumption. Cgroups v2 groups all parent and child processes into a single unified accounting slice, guaranteeing that total collective consumption never exceeds your configured caps.

Step 1: Verify Cgroups v2 Support

Check if your Linux server is running unified cgroups v2:

stat -fc %T /sys/fs/cgroup/

If the output is cgroup2fs, your system is using cgroups v2.

Step 2: Inspect Real-Time Resource Usage with systemd-cgtop

Monitor live CPU, memory, and I/O consumption by cgroup slice:

systemd-cgtop --order=memory

Step 3: Apply Memory and CPU Limits to an Existing Service

Suppose you have a background worker or API service named worker.service. To limit its maximum memory to 1.5GB and CPU usage to 1.5 cores (150%): 

sudo systemctl set-property worker.service MemoryMax=1.5G MemoryHigh=1.2G CPUQuota=150%
Pro Tip: MemoryHigh acts as a throttling throttle. When exceeded, the kernel throttles the processes I/O and aggressively reclaims page cache before hard-killing the service at MemoryMax.

Step 4: Configure Persistent Resource Limits in Unit Files

You can also declare resource controls directly inside your service unit file (e.g., /etc/systemd/system/myapp.service): 

[Unit]
Description=High Load API Worker Service
After=network.target

[Service]
Type=simple
User=appuser
ExecStart=/usr/bin/node /opt/myapp/server.js
Restart=always

# Cgroups v2 Resource Constraints
CPUAccounting=yes
CPUQuota=100%             # Restrict service to maximum 1 CPU core

MemoryAccounting=yes
MemoryHigh=750M           # Begin aggressive page cache reclamation
MemoryMax=1G              # Hard ceiling (OOM killer intervenes if exceeded)

TasksMax=250              # Prevent fork-bomb attacks

# Protect service against host-wide OOM kills
OOMScoreAdjust=-500

[Install]
WantedBy=multi-user.target

Reload systemd and restart the service:

sudo systemctl daemon-reload
sudo systemctl restart myapp.service

Step 5: Verify Active Constraints

Inspect the running service properties to confirm cgroup limits:

systemctl show myapp.service -p MemoryMax,MemoryHigh,CPUQuotaPerSecUSec,TasksMax

You can also check the kernel cgroup interface directly:

cat /sys/fs/cgroup/system.slice/myapp.service/memory.max
cat /sys/fs/cgroup/system.slice/myapp.service/cpu.max

Frequently Asked Questions

What is the advantage of using Systemd Cgroups v2 over older ulimit commands?

ulimit commands only apply limits to individual processes within a single user session shell. If a process spawns child processes or forks background daemons, ulimit fails to constrain aggregate usage. Systemd with Cgroups v2 enforces hierarchical resource boundaries across entire service trees, including all sub-processes and worker threads.

What happens when a service exceeds its MemoryMax allocation?

When a service exceeds its MemoryMax threshold, the Linux kernel Out-Of-Memory (OOM) killer selectively terminates processes within that specific cgroup control slice without crashing the host operating system or terminating other critical services like sshd or databases.

How does CPUQuota calculate percentages for multi-core CPUs?

CPUQuota represents total CPU compute time per scheduling window. 100% corresponds to 1 full CPU core. If your server has 4 CPU cores, setting CPUQuota=200% restricts the service to a maximum of 2 full cores of processing capacity.
