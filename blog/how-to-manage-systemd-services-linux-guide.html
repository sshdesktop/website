How to Manage systemd Services on Linux: Complete 2026 Guide

Published: November 2026 • 10 min read • By SSH Desktop Engineering Team

On modern Linux distributions (Ubuntu, Debian, CentOS, RHEL, Fedora, Arch, and SUSE), systemd is the core init system and service manager responsible for initializing the operating system and managing background daemons.

Whether controlling standard web servers like Nginx and Apache or deploying custom Node.js, Python, or Go microservices that must automatically restart upon crashes or reboots, understanding systemctl and systemd unit files is mandatory.

In this guide, you will master essential systemctl commands, learn how to author production-ready .service unit files, inspect live logs with journalctl, and manage services visually with SSH Desktop.

Essential systemctl Commands Cheatsheet

Command Action When to Use
sudo systemctl start app Starts the service immediately Manual session testing
sudo systemctl stop app Gracefully stops the service Maintenance / upgrades
sudo systemctl restart app Stops then starts the service Deploying new code builds
sudo systemctl reload app Reloads config without dropping connections Nginx / Apache vhost updates
sudo systemctl status app Shows PID, uptime, memory & last 10 logs Troubleshooting health
sudo systemctl enable --now app Enables on boot AND starts immediately New production services
sudo systemctl disable app Prevents service from starting on boot Retiring background services
sudo systemctl daemon-reload Reloads all unit files from disk After editing any .service file

How to Create a Custom systemd Service (Step-by-Step)

Suppose you built a Node.js API or Python web service located at /opt/myapp/server.js. Rather than running it inside a fragile terminal screen, turn it into a managed systemd service:

1. Create the Service File:

sudo nano /etc/systemd/system/myapp.service

2. Author the Unit Configuration:

[Unit]
Description=Node.js Production Application
Documentation=https://example.com/docs
After=network.target mongodb.service

[Service]
Type=simple
User=ubuntu
WorkingDirectory=/opt/myapp
ExecStart=/usr/bin/node /opt/myapp/server.js
Restart=always
RestartSec=5
Environment=NODE_ENV=production PORT=3000
StandardOutput=journal
StandardError=journal

# Security Sandbox Hardening
ProtectSystem=full
NoNewPrivileges=true

[Install]
WantedBy=multi-user.target

Key Directives Decoded:

  • After=network.target: Waits until networking is initialized before starting your app.
  • User=ubuntu: Runs the process as an unprivileged user (never run application code as root!).
  • Restart=always & RestartSec=5: If your application throws an uncaught exception and crashes, systemd will automatically restart it after 5 seconds.
  • WantedBy=multi-user.target: Ensures the service starts when the server reaches standard non-graphical multi-user mode on boot.

3. Reload systemd & Start Your Service:

sudo systemctl daemon-reload
sudo systemctl enable --now myapp
sudo systemctl status myapp

Viewing Logs with journalctl

systemd captures all stdout and stderr from your service into its centralized binary log daemon, systemd-journald.

Essential journalctl Log Commands:

# Tail live logs in real time (like tail -f):
sudo journalctl -u myapp -f

# Show the last 100 lines of logs:
sudo journalctl -u myapp -n 100

# Show logs from today only:
sudo journalctl -u myapp --since today

# Show only errors (priority 3 or higher):
sudo journalctl -u myapp -p err..emerg

Troubleshooting Failed systemd Services

If a service shows Active: failed (Result: exit-code):

  1. Run systemctl status myapp to see the exit code (e.g. status=127/COMMAND_NOT_FOUND or status=1/FAILURE).
  2. Run journalctl -u myapp -e --no-pager to jump to the very end of the error log.
  3. Verify file paths: if ExecStart specifies node instead of the full path /usr/bin/node, systemd will fail. Run which node to find the absolute binary location.
