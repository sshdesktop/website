The Complete Linux Crontab Guide: Syntax, Examples & Best Practices (2026)

Published: November 2026 • 10 min read • By SSH Desktop Engineering Team

Automating repetitive system maintenance tasks — running nightly database backups, rotating logs, renewing Let's Encrypt SSL certificates, and syncing remote files — is a core responsibility of any Linux system administrator.

For over 40 years, the de facto standard tool for scheduled task automation on Unix-like operating systems has been the cron daemon.

In this definitive guide, you will master crontab syntax, explore common schedule patterns, debug the infamous "runs in terminal but fails in cron" environment trap, and learn how to manage scheduled tasks visually with SSH Desktop.

Crontab Syntax Anatomy: The 5 Fields

A standard user crontab entry consists of five time/date expressions followed by the shell command to execute:

* * * * * command_to_execute
┬ ┬ ┬ ┬ ┬
│ │ │ │ └─── Day of the week (0 - 7) (0 and 7 are Sunday)
│ │ │ └───── Month (1 - 12)
│ │ └─────── Day of the month (1 - 31)
│ └───────── Hour (0 - 23)
└─────────── Minute (0 - 59)

Special Characters Decoded:

  • * (Asterisk): Represents "every" value (e.g. * in month means every month).
  • , (Comma): Value list separator (e.g. 1,15,30 in minute field).
  • - (Hyphen): Defines an inclusive range (e.g. 1-5 in day of week for Monday through Friday).
  • / (Slash): Specifies step values (e.g. */10 in minute field means every 10 minutes).

10 Real-World Crontab Schedule Examples

Schedule Expression When It Runs Common Use Case
* * * * * Every single minute Queue monitoring / health checks
*/5 * * * * Every 5 minutes API polling & metrics collection

Managing Crontab Files

Never edit crontab spool files in /var/spool/cron/crontabs/ directly. Always use the crontab utility:

# Edit the current user's crontab:
crontab -e

# List all active cron jobs for current user:
crontab -l

# Remove all cron jobs for current user (be careful!):
crontab -r

# Edit another user's crontab (requires root):
sudo crontab -u www-data -e

The #1 Cron Trap: Missing Environment Variables

The single most common bug with cron jobs is: "My script runs perfectly when I type it in the terminal, but nothing happens when cron runs it!"

When you log in via SSH, your shell sources ~/.bashrc, ~/.profile, and sets a rich PATH containing Node, Python, and local binaries.

Cron runs in a minimal, non-interactive shell. Its default PATH is usually restricted to /usr/bin:/bin.

The Solution:

  1. Use Absolute Paths: Instead of python3 script.py, write /usr/bin/python3 /home/ubuntu/script.py.
  2. Define PATH at the Top of Crontab: Add explicit environment variables to your crontab:
SHELL=/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/sbin:/bin:/usr/sbin:/usr/bin
MAILTO=admin@example.com

0 2 * * * /usr/bin/python3 /home/ubuntu/backup.py >> /var/log/backup.log 2>&1

Redirecting Logs & Silencing Output

By default, if a cron job produces output, the daemon attempts to email it via local mail (sendmail). On modern cloud servers without local mail agents, output is silently discarded or clutters /var/log/syslog.

1. Append Output & Errors to a Dedicated Log File:

0 4 * * * /opt/scripts/cleanup.sh >> /var/log/cleanup.log 2>&1

2. Discard All Output Completely (Run Silently):

*/15 * * * * /usr/bin/php /var/www/artisan schedule:run > /dev/null 2>&1
