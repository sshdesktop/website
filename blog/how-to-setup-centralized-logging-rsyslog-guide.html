How to Set Up Centralized Remote Logging with Rsyslog: 2026 Guide

When managing a fleet of Linux servers, logging in to each machine individually to investigate authentication failures or system anomalies is inefficient and insecure. If a server is compromised, attackers frequently wipe local log files to hide their tracks. Learn how to configure centralized remote syslog forwarding with rsyslog over encrypted TCP in 2026.

Centralized Logging Architecture

In an enterprise rsyslog architecture, one dedicated hardened server acts as the Log Receiver, while individual application and database nodes act as Log Forwarders (Clients). Logs generated by systemd journal, OpenSSH, UFW, and Nginx are streamed over TCP directly to the receiver.

Part 1: Configure the Central Rsyslog Server (Receiver)

On your central logging server, edit /etc/rsyslog.conf:

sudo nano /etc/rsyslog.conf

Enable the TCP syslog reception module by uncommenting:

# Enable TCP syslog reception
module(load="imtcp")
input(type="imtcp" port="514")

Create a custom template to organize incoming logs into subdirectories per client hostname. Create /etc/rsyslog.d/30-remote-clients.conf: 

template(name="RemoteClients" type="string" string="/var/log/remote/%HOSTNAME%/%PROGRAMNAME%.log")

# Store all remote incoming logs using the template
if ($fromhost-ip != '127.0.0.1') then {
    action(type="omfile" dirmicrosecond="on" dirmode="0755" filemode="0640" dircached="on" dynafiles="RemoteClients")
    stop
}

Restart rsyslog on the central server and open port 514 in your firewall:

sudo systemctl restart rsyslog
sudo ufw allow from 10.0.0.0/8 to any port 514 proto tcp

Part 2: Configure Client Nodes to Forward Logs

On each client server, create a forwarding rule with a disk queue to ensure zero log loss during network interruptions:

sudo nano /etc/rsyslog.d/50-forward.conf

Add the following configuration (replace 10.0.0.100 with your central server IP):

# Configure local buffer queue for reliability
$ActionQueueFileName fwdRule1      # Unique name prefix for spool files
$ActionQueueMaxDiskSpace 1g        # 1GB disk buffer limit
$ActionQueueSaveOnShutdown on      # Save in-memory data if client reboots
$ActionQueueType LinkedList        # Run asynchronously
$ActionResumeRetryCount -1         # Infinite retries if central server offline

# Forward all logs over TCP
*.* action(type="omfwd" target="10.0.0.100" port="514" protocol="tcp")

Restart the client rsyslog daemon:

sudo systemctl restart rsyslog

Part 3: Verify Log Streaming

Generate a test log entry on the client node:

logger "TEST_SYSLOG_CENTRAL_LOGGING_VERIFICATION"

On the central log server, check if the message arrived in the client directory:

sudo tail -f /var/log/remote/*/syslog.log

Frequently Asked Questions

Why should I use TCP instead of UDP for remote syslog forwarding?

UDP (port 514) is connectionless and drops packets silently under network congestion or high traffic bursts. TCP (port 514) provides guaranteed delivery, packet retransmission, and supports TLS encryption to protect sensitive authentication logs from wiretapping.

What happens to logs on the client if the central rsyslog server goes down?

Rsyslog includes an action queue mechanism. By configuring a disk-assisted queue (ActionQueueType LinkedList), client machines will buffer logs in local RAM and disk until the central logging server comes back online, preventing log loss.

How does centralized logging help with compliance audits (SOC 2, ISO 27001)?

Centralized logging ensures an immutable audit trail. Even if an attacker gains root access on a web server and deletes /var/log/auth.log, the centralized log server already has the forwarded connection and command records stored safely offsite.
