How to Set Up a Chroot SFTP Jail on Linux: 2026 Guide

When external clients, contractors, or automated third-party tools need to upload files to your Linux server, granting them standard SSH shell access is a massive security hazard. A Chroot SFTP Jail locks users into their designated directory tree, hiding the root filesystem, /etc/passwd, and environment variables, while strictly disabling terminal shell execution. Learn how to configure a secure SFTP jail in 2026.

How ChrootDirectory and internal-sftp Work

The OpenSSH daemon provides a native subsystem called internal-sftp. Combined with the ChrootDirectory directive, it alters the root directory (/) for matching users, making it physically impossible for them to navigate outside their assigned directory tree.

Step 1: Create a Dedicated SFTP Group and User

Create a dedicated group for jailed SFTP accounts:

sudo groupadd sftp_users

Create a new user with shell disabled (/sbin/nologin) and assigned to the group:

sudo useradd -g sftp_users -d /home/sftpclient -s /sbin/nologin sftpclient

# Set password (or configure SSH key authentication)
sudo passwd sftpclient

Step 2: Configure Directory Permissions (The Root Ownership Rule)

OpenSSH strictly mandates that the chroot directory itself must be owned by root and not writable by any other user: 

# The chroot jail root must be owned by root:root
sudo chown root:root /home/sftpclient
sudo chmod 755 /home/sftpclient

# Create a writable directory inside where the user can upload files
sudo mkdir -p /home/sftpclient/uploads
sudo chown sftpclient:sftp_users /home/sftpclient/uploads
sudo chmod 775 /home/sftpclient/uploads

Step 3: Configure OpenSSH sshd_config

Edit the OpenSSH configuration file at /etc/ssh/sshd_config:

sudo nano /etc/ssh/sshd_config

1. Ensure the internal SFTP subsystem is enabled:

# Replace Subsystem sftp /usr/lib/openssh/sftp-server with:
Subsystem sftp internal-sftp

2. Append the Match Group block at the very bottom of the file:

Match Group sftp_users
    ChrootDirectory %h
    ForceCommand internal-sftp
    AllowTcpForwarding no
    X11Forwarding no
    PasswordAuthentication yes
  • %h: Dynamically resolves to the user's home directory.
  • ForceCommand internal-sftp: Disallows shell access, forcing SFTP protocol only.
  • AllowTcpForwarding no: Disables SSH tunneling and port forwarding bypasses.

Step 4: Test Syntax and Restart SSH

Verify syntax before restarting OpenSSH:

sudo sshd -t
sudo systemctl restart ssh || sudo systemctl restart sshd

Step 5: Verify the Chroot Jail

1. Test that terminal SSH shell access is rejected:

ssh sftpclient@your-server-ip
# Output: This service allows sftp connections only. Connection to server closed.

2. Connect via SFTP:

sftp sftpclient@your-server-ip
sftp> pwd
Remote working directory: /
sftp> cd uploads
sftp> put testfile.txt
Uploading testfile.txt to /uploads/testfile.txt
sftp> cd ..
sftp> cd ..
sftp> ls
uploads

The client cannot escape the chroot root folder.

Frequently Asked Questions

Why does OpenSSH reject logins with "fatal: bad ownership or modes for chroot directory"?

OpenSSH enforces strict security requirements on ChrootDirectory paths: the target directory and all parent directories in the path MUST be owned by root and cannot be writable by any other user or group (permissions must be 755 or 750). To allow uploads, create a writable subdirectory (e.g., uploads/) inside the chroot.

What is the advantage of ForceCommand internal-sftp over /usr/lib/openssh/sftp-server?

internal-sftp is built directly into the sshd process binary. It does not require spawning a separate shell or copying /bin/sh, libraries, or device files into the chroot jail, drastically simplifying security configuration.

Can a jailed SFTP user execute terminal commands or run bash scripts?

No. When configured with ForceCommand internal-sftp and shell /usr/sbin/nologin (or /bin/false), any attempt to establish an interactive SSH shell is immediately terminated by the server.
