How to Set Up Let's Encrypt Wildcard SSL with Certbot (DNS-01 Guide)

When managing SaaS platforms, multi-tenant customer applications, or staging environments, requesting separate SSL certificates for every new subdomain is tedious and triggers Let's Encrypt rate limits. A single wildcard certificate (*.example.com) covers unlimited subdomains under one cryptographic key. Learn how to automate wildcard SSL generation using Certbot and DNS-01 validation in 2026.

How DNS-01 Validation Works

Because wildcard certificates can represent any subdomain, Let's Encrypt cannot verify ownership by looking for a file on port 80. Instead, Certbot creates a temporary DNS TXT record at _acme-challenge.example.com. Once Let's Encrypt verifies the TXT record via authoritative DNS nameservers, the certificate is issued, and Certbot cleans up the record.

Step 1: Install Certbot and Cloudflare DNS Plugin

Install the certbot snap package with the official Cloudflare plugin:

sudo snap install --classic certbot
sudo snap set certbot trust-plugin-with-root=ok
sudo snap install certbot-dns-cloudflare

Step 2: Generate Scoped Cloudflare API Token

In your Cloudflare dashboard, navigate to My Profile > API Tokens > Create Token. Use the Edit Zone DNS template, restrict permissions to Zone - DNS - Edit, and restrict Zone Resources to your specific domain.

Store the token on your server with strict permissions:

sudo mkdir -p /etc/letsencrypt
sudo nano /etc/letsencrypt/cloudflare.ini

Add your API token:

dns_cloudflare_api_token = 1234567890abcdef1234567890abcdef12345678

Protect the file so only root can read it:

sudo chmod 600 /etc/letsencrypt/cloudflare.ini

Step 3: Request the Wildcard Certificate

Execute Certbot targeting both the apex domain and the wildcard pattern:

sudo certbot certonly \
  --dns-cloudflare \
  --dns-cloudflare-credentials /etc/letsencrypt/cloudflare.ini \
  --dns-cloudflare-propagation-seconds 30 \
  -d example.com \
  -d "*.example.com" \
  --email admin@example.com \
  --agree-tos \
  --no-eff-email

The certificate and private key will be saved to: /etc/letsencrypt/live/example.com/fullchain.pem and privkey.pem.

Step 4: Configure Nginx to Use the Wildcard Certificate

You can now reference this single certificate across all server blocks:

# Handles api.example.com, app.example.com, admin.example.com, etc.
server {
    listen 443 ssl http2;
    server_name ~^(?<subdomain>.+)\.example\.com$;

    ssl_certificate /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    location / {
        proxy_pass http://localhost:4000;
        include proxy_params;
    }
}

Step 5: Automated Renewal Hook

Test automatic renewal with a dry run:

sudo certbot renew --dry-run

Configure Nginx to reload automatically after renewals in /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh:

#!/usr/bin/env bash
systemctl reload nginx
sudo chmod +x /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh

Frequently Asked Questions

Why can't I generate a wildcard certificate using HTTP-01 webroot challenge?

The ACME specification strictly mandates DNS-01 verification for wildcard certificates (*.domain.com). Proving ownership of an arbitrary subdomain requires creating a TXT record (_acme-challenge.domain.com) in the authoritative DNS zone, which standard webroot file placement cannot prove.

Can Certbot automatically renew wildcard certificates without manual DNS intervention?

Yes. By installing a DNS plugin (such as certbot-dns-cloudflare or certbot-dns-route53) and providing scoped DNS API credentials, Certbot creates the TXT record, validates ownership, deletes the record, and reloads Nginx automatically every 60 days.

Does a wildcard certificate for *.example.com also cover the root apex domain example.com?

No. A certificate for *.example.com only covers subdomains (e.g., app.example.com, api.example.com). Always request both domains in a single command: -d example.com -d "*.example.com".
