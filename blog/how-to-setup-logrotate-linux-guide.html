How to Set Up Logrotate on Linux: Complete 2026 Guide

Uncontrolled log file growth is one of the leading causes of production server outages. When /var/log fills to 100%, database transactions fail, systemd cannot spawn new processes, and SSH logins become impossible. logrotate automates log rotation, gzip compression, scheduled pruning, and daemon reloads. Learn how to configure robust log rotation for custom apps and web servers in 2026.

How Logrotate Operates Under Systemd

Modern Linux distributions run logrotate via a daily systemd timer (logrotate.timer) rather than a traditional cron job. When triggered, it parses the main configuration file at /etc/logrotate.conf along with all modular configuration files located in /etc/logrotate.d/.

Step 1: Anatomy of a Production Logrotate File

Create a new logrotate configuration for a custom application or microservice: 

sudo nano /etc/logrotate.d/myapp

Paste the following production-grade configuration:

/var/log/myapp/*.log {
    daily
    missingok
    rotate 14
    compress
    delaycompress
    notifempty
    create 0640 myapp adm
    sharedscripts
    dateext
    postrotate
        /bin/systemctl reload myapp.service > /dev/null 2>&1 || true
    endscript
}

Directives Explained

  • daily: Rotates logs once every 24 hours. (Can also be weekly, monthly, or size-based like size 100M).
  • rotate 14: Retains 14 rotated archives before deleting the oldest file.
  • compress: Compresses rotated files using gzip, reducing log footprint by up to 90%.
  • delaycompress: Delays compression until the next rotation cycle, ensuring active processes are not locked.
  • missingok: Prevents errors if the log file is absent.
  • notifempty: Skips rotation if the log file is 0 bytes.
  • copytruncate: Truncates the original file in place instead of moving it (ideal for daemons that cannot be reloaded).
  • dateext: Appends date stamps (YYYYMMDD) instead of sequential numbers (.1, .2).

Step 2: Testing and Debugging Logrotate

Before leaving your new rule to the daily timer, test it in dry-run mode:

# Dry run: Test syntax and actions without modifying files
sudo logrotate -d /etc/logrotate.d/myapp

# Force execution: Rotate files immediately with verbose output
sudo logrotate -vf /etc/logrotate.d/myapp

Step 3: Inspecting Rotation Status

View when each managed log file was last rotated:

sudo cat /var/lib/logrotate/status | grep myapp

Check the systemd timer schedule:

systemctl list-timers | grep logrotate

Frequently Asked Questions

Why does logrotate fail to release disk space after rotating a log file?

If a running daemon (like Nginx, Apache, or a Node.js process) holds an open file descriptor, deleting or moving the file will not release disk space. You must use copytruncate or send a USR1 reload signal in a postrotate script so the daemon reopens the new log file.

How do I force logrotate to run immediately for testing?

Run sudo logrotate -vf /etc/logrotate.d/your-config. The -v flag enables verbose output so you can see each step, and -f forces log rotation even if the scheduled frequency or size criteria have not yet been met.

Where are logrotate status and execution logs stored?

Logrotate records the timestamp of the last rotation in /var/lib/logrotate/status (or /var/lib/logrotate.status). Systemd timer logs can be inspected via journalctl -u logrotate.service.
