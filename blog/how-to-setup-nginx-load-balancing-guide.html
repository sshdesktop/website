How to Set Up Nginx Load Balancing (Round Robin, Least Conn, IP Hash): 2026 Guide

High Availability By SSH Desktop Engineering Team • Updated November 2026 • 10 min read

As web applications grow beyond a single virtual server, distributing HTTP requests across a pool of application workers is required to achieve horizontal scalability and zero-downtime deployments. Nginx is the industry's premier open-source software load balancer, capable of handling tens of thousands of concurrent connections with minimal memory overhead.

Executive Summary

Nginx load balancing is configured using an upstream block that defines your backend server pool. In this guide, you will learn how to configure Round Robin, Least Connections, and IP Hash algorithms, set server weights, enable passive health checks, and manage multi-server clusters visually using SSH Desktop Multi-Server Automation.

1. The Core Nginx Upstream Configuration

In your Nginx configuration (e.g. /etc/nginx/conf.d/loadbalancer.conf), define the backend cluster inside an upstream block, then reference it using proxy_pass: 

upstream backend_cluster {
    # Default: Round Robin algorithm
    server 10.0.0.11:3000;
    server 10.0.0.12:3000;
    server 10.0.0.13:3000;
}

server {
    listen 80;
    server_name api.example.com;

    location / {
        proxy_pass http://backend_cluster;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

2. Understanding Nginx Load Balancing Algorithms

Algorithm Directive Best Used For
Round Robin (Default) (None needed) Homogeneous servers with short, uniform requests (REST APIs)
Least Connections least_conn; Varying request times (file conversions, heavy DB queries, SSR)
IP Hash ip_hash; Stateful applications requiring sticky visitor sessions
Generic Hash hash $request_uri; Consistent caching proxies and deterministic routing

Example: Least Connections with Weighted Distribution

If one server in your cluster has double the CPU and RAM of the others, use the weight parameter: 

upstream backend_cluster {
    least_conn;

    # Primary high-spec server receives 3x traffic:
    server 10.0.0.11:3000 weight=3;

    # Standard servers:
    server 10.0.0.12:3000 weight=1;
    server 10.0.0.13:3000 weight=1;

    # Backup server (only receives traffic if all others are down):
    server 10.0.0.99:3000 backup;
}

3. Passive Health Checks & Automatic Failover

Nginx automatically detects unresponsive upstream nodes and removes them from the routing rotation using max_fails and fail_timeout: 

upstream backend_cluster {
    # If 3 consecutive requests fail within 30s, mark node down for 30s:
    server 10.0.0.11:3000 max_fails=3 fail_timeout=30s;
    server 10.0.0.12:3000 max_fails=3 fail_timeout=30s;
}

4. Frequently Asked Questions

What is the default load balancing algorithm in Nginx?

The default algorithm is Round Robin. Incoming requests are distributed sequentially across all listed upstream backend servers in equal order.

When should I use least_conn instead of round-robin?

Use least_conn when backend requests take varying amounts of time to complete (e.g. file uploads, complex database queries, report generation). It routes new requests to the backend server with the lowest number of active connections, preventing single servers from becoming overloaded.

How do I maintain user sessions across balanced servers without Redis?

Use the ip_hash directive in your upstream block. Nginx hashes the client's IPv4 address (or first 3 octets) to ensure that requests from the same visitor consistently route to the same backend server, maintaining in-memory session state.
