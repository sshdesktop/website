How to Configure Nginx Rate Limiting to Stop DDoS & Brute-Force Attacks (2026)

Web scrapers, credential-stuffing bots, and volumetric HTTP floods can quickly overwhelm application servers and exhaust database connection pools. Nginx provides a powerful, built-in rate-limiting module based on the leaky bucket algorithm. Learn how to configure granular rate limits for APIs, login endpoints, and static assets in 2026.

How Nginx Rate Limiting Works (Leaky Bucket)

The leaky bucket algorithm visualizes requests as drops entering a bucket with a fixed drain rate. If incoming requests arrive faster than the drain rate, the bucket fills up. Once the bucket overflows, excess requests are rejected immediately with an HTTP 503 (Service Temporarily Unavailable) or HTTP 429 (Too Many Requests) status code.

Step 1: Define the Shared Memory Zone in nginx.conf

Rate-limiting zones must be declared within the http { ... } context, typically in /etc/nginx/nginx.conf:

http {
    # Allocate 10MB memory zone 'login_limit' allowing 5 requests per minute per IP
    limit_req_zone $binary_remote_addr zone=login_limit:10m rate=5r/m;

    # Allocate 10MB memory zone 'api_limit' allowing 30 requests per second per IP
    limit_req_zone $binary_remote_addr zone=api_limit:10m rate=30r/s;

    # Change default 503 status to standard 429 Too Many Requests
    limit_req_status 429;
}

Using $binary_remote_addr uses only 4 bytes (IPv4) or 16 bytes (IPv6) per client IP, allowing a 10MB zone to store approximately 160,000 distinct IP addresses.

Step 2: Apply Rate Limits to Specific Location Blocks

In your virtual host configuration (e.g., /etc/nginx/sites-available/example.com), apply the defined zones to sensitive URIs:

server {
    server_name api.example.com;

    # Protect login and authentication routes against brute-force attacks
    location /api/v1/auth/login {
        # Burst of 3 requests allowed, processed without delay
        limit_req zone=login_limit burst=3 nodelay;
        
        proxy_pass http://backend_upstream;
        include proxy_params;
    }

    # General API rate limiting with smooth burst buffering
    location /api/ {
        limit_req zone=api_limit burst=20 nodelay;
        
        proxy_pass http://backend_upstream;
        include proxy_params;
    }
}

Step 3: Handling Rate Limits Behind Cloudflare or Proxies

If your server sits behind Cloudflare, AWS ALB, or a reverse proxy, you must restore the visitor's real IP address before applying rate limits. Otherwise, all visitors will share the proxy IP and trigger premature 429 errors: 

# In http { ... } or server { ... } block
set_real_ip_from 173.245.48.0/20;
set_real_ip_from 103.21.244.0/22;
# (Add all Cloudflare IP ranges)

real_ip_header CF-Connecting-IP;

Step 4: Test and Monitor Rate Limiting

Test your rate-limiting rules using curl in a quick bash loop:

for i in {1..10}; do curl -s -o /dev/null -w "%{http_code}\n" https://api.example.com/api/v1/auth/login; done

You should see initial 200 responses followed immediately by 429 responses as the burst ceiling is exceeded.

Frequently Asked Questions

What is the difference between limit_req and limit_conn in Nginx?

limit_req limits the frequency or rate of HTTP requests per second/minute (leaky bucket algorithm). limit_conn limits the number of concurrent active TCP connections opened by a single client IP address.

What does the nodelay parameter do in Nginx rate limiting?

The burst parameter creates a queue for temporary traffic spikes. By default, queued requests are delayed to match the rate limit. Adding nodelay processes burst requests immediately while still rejecting any requests that exceed the burst ceiling.

How does Nginx rate limiting work behind Cloudflare or a load balancer?

If Nginx sits behind a CDN or proxy, using $binary_remote_addr will rate limit the proxy IP instead of the visitor. Configure real_ip_header CF-Connecting-IP (or X-Forwarded-For) with set_real_ip_from directives so Nginx evaluates true visitor IPs.
