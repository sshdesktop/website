How to Configure Nginx WebSocket Reverse Proxy: 2026 Guide

Modern real-time applications (chat systems, live dashboards, collaborative canvases, and gaming backends) rely on WebSockets (ws:// and wss://) for full-duplex communication. However, when placing applications (Node.js, Socket.io, Django Channels, or Python FastAPI) behind Nginx, developers frequently encounter WebSocket connection failed: Error during WebSocket handshake: Unexpected response code: 400 or sudden 60-second timeouts. Learn how to configure robust WebSocket reverse proxies in 2026.

How WebSocket Handshakes Work Across Proxies

A WebSocket session begins as a standard HTTP/1.1 request containing special upgrade headers: 

GET /socket.io/?EIO=4&transport=websocket HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

Because HTTP hop-by-hop headers are removed by default reverse proxies, Nginx must be explicitly instructed to pass the Upgrade and Connection headers upstream and keep the underlying TCP socket open.

Step 1: Define the Dynamic Connection Map in nginx.conf

The cleanest architectural approach uses an Nginx map directive inside the http {} block of /etc/nginx/nginx.conf: 

http {
    # Dynamically set Connection header based on Upgrade request
    map $http_upgrade $connection_upgrade {
        default upgrade;
        ''      close;
    }

    include /etc/nginx/sites-enabled/*;
}

If the client requests an HTTP upgrade, Nginx sets $connection_upgrade to upgrade; otherwise, it falls back to standard HTTP connection reuse.

Step 2: Configure Virtual Host with WebSocket Directives

Edit your site configuration file (e.g., /etc/nginx/sites-available/app.example.com): 

server {
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    server_name app.example.com;

    # TLS Certificates
    ssl_certificate /etc/letsencrypt/live/app.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/app.example.com/privkey.pem;

    # Dedicated WebSocket or API Location
    location /ws/ {
        proxy_pass http://127.0.0.1:4000;
        proxy_http_version 1.1;

        # WebSocket Upgrade Headers
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;

        # Standard Forwarding Headers
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # Prevent 60-second idle disconnects (Set to 24 hours)
        proxy_read_timeout 86400s;
        proxy_send_timeout 86400s;

        # Disable proxy buffering for real-time latency
        proxy_buffering off;
    }

    # Standard Web Frontend
    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

Step 3: Test Configuration and Reload Nginx

Validate syntax before reloading:

sudo nginx -t && sudo systemctl reload nginx

Step 4: Verify WebSocket Handshake with wscat

Test the encrypted WebSocket endpoint directly using the wscat CLI utility:

# Install wscat
npm install -g wscat

# Test encrypted WebSocket connection
wscat -c wss://app.example.com/ws/

Once connected, type a message or JSON payload: 

Connected (press CTRL+C to quit)
> {"type": "ping"}
< {"type": "pong", "status": "active"}

If the connection stays active past 60 seconds without dropping, your timeout parameters and reverse proxy headers are operating properly.

Frequently Asked Questions

Why do WebSockets fail with 400 Bad Request or 502 Bad Gateway behind Nginx?

By default, Nginx treats upstream proxy connections as standard HTTP/1.0 and strips hop-by-hop headers including Upgrade and Connection. Without explicitly passing proxy_set_header Upgrade $http_upgrade and proxy_set_header Connection "upgrade", the backend application never receives the WebSocket handshake.

Why do WebSocket connections drop after exactly 60 seconds of inactivity?

The default proxy_read_timeout in Nginx is 60 seconds. If neither client nor server transmits data or ping/pong heartbeats within that window, Nginx terminates the TCP socket. Setting proxy_read_timeout to 3600s or 86400s keeps long-lived connections open.

What is the advantage of using an Nginx map block for WebSocket connections?

The map block dynamically inspects the client request: if an Upgrade header is present, Connection is set to upgrade; otherwise, it is set to close. This allows a single Nginx location block to serve both standard REST API requests and WebSockets efficiently.
