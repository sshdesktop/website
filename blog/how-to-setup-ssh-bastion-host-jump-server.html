How to Set Up an SSH Bastion Host (Jump Server): Complete Architecture Guide (2026)

Published: November 2026 • 11 min read • By SSH Desktop Engineering Team

In modern cloud infrastructure (Amazon Web Services, Google Cloud, Azure, and private OpenStack clouds), placing every server on a public IPv4 address is an architectural anti-pattern.

Instead, enterprise security models place databases, application workers, and caching layers in isolated Private Subnets with internal IP addresses (e.g. 10.0.x.x). To administer these private machines, engineers route their traffic through a dedicated, heavily audited gateway known as a Bastion Host or Jump Server.

In this guide, you will learn the security mechanics of bastion hosts, how to configure multi-hop routing using modern ProxyJump, why legacy SSH agent forwarding is dangerous, and how to harden a bastion server against intrusion.

Cloud Network Topology: Public Subnet vs Private Subnet

A well-architected cloud VPC (Virtual Private Cloud) separates exposure into two zones:

  • Public Subnet (Internet-Facing): Contains the Internet Gateway, load balancers, and a single, locked-down Bastion Host. The bastion has a public IP address and accepts inbound SSH strictly from authorized administrator IPs.
  • Private Subnet (Zero Internet Inbound): Contains production database clusters (PostgreSQL, MySQL), internal microservices, and Kubernetes worker nodes. These nodes have NO public IPs and reject all inbound traffic except connections originating from the Bastion's internal IP.

Step 1: Connecting via CLI (The Modern ProxyJump Syntax)

In older tutorials, developers were taught to SSH into the bastion, wait for a prompt, and then run a second SSH command from the bastion to the target. This required storing private keys on the bastion — a critical security hazard!

With modern OpenSSH, you use the -J (ProxyJump) flag:

ssh -J ec2-user@bastion.example.com ubuntu@10.0.2.45

If the bastion uses a custom port or key:

ssh -J ec2-user@bastion.example.com:2222 -i ~/.ssh/internal_key.pem ubuntu@10.0.2.45

Why ProxyJump Is Better Than SSH Agent Forwarding (ssh -A):

Security Warning: Never use ssh -A (Agent Forwarding) on untrusted jump servers. When agent forwarding is active, a malicious user or attacker with root privileges on the bastion can access your local agent's UNIX socket ($SSH_AUTH_SOCK) and authenticate to your other servers using your private keys.

ProxyJump does NOT forward keys. Instead, it commands the bastion to act as a raw TCP proxy via nc or sshd -W. The SSH handshake occurs directly between your local laptop and the internal target. The bastion only ever sees encrypted ciphertext.

Step 2: Permanent ~/.ssh/config Configuration

Typing -J on every command is repetitive. Add both entries to your local ~/.ssh/config:

# 1. The Bastion Gateway
Host bastion
HostName 198.51.100.10
User ec2-user
IdentityFile ~/.ssh/bastion_key.pem

# 2. Private App Server in VPC
Host app-server
HostName 10.0.2.45
User ubuntu
IdentityFile ~/.ssh/internal_key.pem
ProxyJump bastion

# 3. Wildcard for ALL 10.0.* Internal Nodes
Host 10.0.*
User ubuntu
IdentityFile ~/.ssh/internal_key.pem
ProxyJump bastion

Now, you can connect directly with:

ssh app-server
# Or connect directly to any private IP:
ssh 10.0.2.78

Step 3: Transferring Files Through the Bastion (SFTP & SCP)

Because OpenSSH handles ProxyJump at the transport layer, file transfers work seamlessly over the bastion:

# SCP through bastion:
scp -J ec2-user@bastion.example.com ./app.tar.gz ubuntu@10.0.2.45:/opt/apps/

# Or using the config alias:
scp ./app.tar.gz app-server:/opt/apps/

Step 4: Hardening the Bastion Server (Production Checklist)

Because the Bastion is the sole gatekeeper to your private network, it must be hardened ruthlessly:

Security Control Implementation Directive Benefit
Disable Passwords PasswordAuthentication no Renders brute-force attacks impossible
Disable Root Login PermitRootLogin no Forces individual named user accounts for audits
IP Allowlisting Security Group: allow port 22 only from Office VPN IP Blocks 100% of unauthorized public traffic
Multi-Factor Authentication Google Authenticator PAM module / FIDO2 Guarantees second-factor cryptographic challenge
Automated Ban Rules Install fail2ban Bans scanning IPs automatically after 3 bad tries
Session Auditing Enable teleport or systemd auditd Logs every keystroke typed on internal infrastructure
