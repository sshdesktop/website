How to Set Up SSH Certificates for Scalable Fleet Access: 2026 Guide

In growing engineering teams, managing ~/.ssh/authorized_keys files across dozens of cloud servers quickly devolves into an unmaintainable security nightmare. Revoking access for a departed engineer requires finding and deleting their public key on every single instance. OpenSSH Certificates solve this by introducing an SSH Certificate Authority (CA). Learn how to configure modern SSH certificate infrastructure in 2026.

The Architecture of SSH Certificate Authentication

Instead of copying individual developer public keys to every server, each server is configured to trust a single CA Public Key (/etc/ssh/ssh_user_ca.pub).

When an engineer requests access, your internal identity provider or CA issues a signed certificate (id_ed25519-cert.pub) valid for a limited window (e.g., 8 hours). The target server verifies the cryptographic signature locally without needing internet access or LDAP lookups.

Step 1: Generate the SSH Certificate Authority (CA) Keypair

On a dedicated, secure machine (or offline hardware key), generate the CA key:

# Generate CA keypair with high-security pass-phrase
ssh-keygen -t ed25519 -C "SSH-Fleet-Certificate-Authority" -f ~/.ssh/ssh_user_ca

Step 2: Configure Remote Servers to Trust the CA

1. Copy the public key (ssh_user_ca.pub) to every remote server at /etc/ssh/ssh_user_ca.pub.

2. Edit /etc/ssh/sshd_config on the target servers:

# Trust certificates signed by this CA
TrustedUserCAKeys /etc/ssh/ssh_user_ca.pub

3. Restart the OpenSSH daemon:

sudo systemctl restart ssh || sudo systemctl restart sshd

Step 3: Issue a Signed Certificate for an Engineer

Sign a developer's public key (id_ed25519.pub) granting specific principals and an 8-hour expiration window: 

ssh-keygen -s ~/.ssh/ssh_user_ca \
  -I "john_doe_session_01" \
  -n "ubuntu,debian,devops" \
  -V -5m:+8h \
  ~/.ssh/id_ed25519.pub

This outputs ~/.ssh/id_ed25519-cert.pub.

Step 4: Inspect Certificate Details

Verify certificate validity, serial number, and allowed principals:

ssh-keygen -L -f ~/.ssh/id_ed25519-cert.pub
Type: ssh-ed25519-cert-v01@openssh.com user certificate
Key ID: "john_doe_session_01"
Principals: 
    ubuntu
    debian
    devops
Valid: from 2026-11-16T08:00:00 to 2026-11-16T16:00:00

Step 5: Connect Without Any authorized_keys on the Server

Connect from the client machine:

ssh -i ~/.ssh/id_ed25519 -i ~/.ssh/id_ed25519-cert.pub ubuntu@your-server-ip

The server validates the CA signature and permits login immediately—even if ~/.ssh/authorized_keys is completely empty!

Frequently Asked Questions

Why are SSH Certificates superior to ~/.ssh/authorized_keys files?

Managing ~/.ssh/authorized_keys across 500 servers requires updating every single server whenever an employee joins or leaves. With SSH Certificates, servers only trust a single Certificate Authority public key. When an employee authenticates, they present a short-lived cryptographically signed certificate (e.g., valid for 8 hours), completely eliminating key rotation on individual servers.

What is an SSH principal?

An SSH principal is a role or username embedded inside the certificate (e.g., ubuntu, root, dev-admin). When a user connects to a server, the server validates whether the requested login account matches one of the authorized principals signed by the CA.

Can SSH certificates automatically expire?

Yes. Every SSH certificate includes a validity window (e.g., -V -5m:+8h). Once the window closes, OpenSSH automatically rejects the certificate, rendering stolen keys useless without requiring server-side key revoking.
