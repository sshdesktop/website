How to Set Up Automatic Security Updates on Ubuntu & Debian: 2026 Guide

Unpatched security vulnerabilities are the primary entry point for automated exploits targeting Linux servers. In 2026, manual patching routines are simply too slow to counter zero-day disclosures. Learn how to configure unattended-upgrades on Ubuntu and Debian to automatically apply critical security patches, manage kernel reboots during maintenance windows, and inspect upgrade logs visually.

Why Automatic Security Updates Are Essential

Linux distributions like Ubuntu and Debian split package repositories into distinct channels: regular software updates and dedicated security channels (e.g., noble-security, bookworm-security). While major package upgrades carry a small risk of configuration changes, security patches specifically address Common Vulnerabilities and Exposures (CVEs) while preserving backwards compatibility.

Best Practice: Restrict automatic updates strictly to security origins. Do not auto-update development libraries or experimental PPAs on production web or database servers.

Step 1: Install and Enable unattended-upgrades

On modern Ubuntu (22.04, 24.04 LTS) and Debian 11/12 systems, install the package and update helper tools:

# Update package indexes
sudo apt update

# Install unattended-upgrades and update-notifier-common
sudo apt install -y unattended-upgrades update-notifier-common

# Enable the systemd service and daily timer
sudo dpkg-reconfigure -plow unattended-upgrades

When prompted by the ncurses dialogue, select Yes to enable automatic downloads and installations.

Step 2: Configure Allowed Package Origins

Edit the main configuration file at /etc/apt/apt.conf.d/50unattended-upgrades:

sudo nano /etc/apt/apt.conf.d/50unattended-upgrades

Ensure the security origin matching your distribution is uncommented. For Ubuntu 24.04 (Noble), verify:

Unattended-Upgrade::Allowed-Origins {
    "${distro_id}:${distro_codename}-security";
    // "${distro_id}:${distro_codename}-updates"; // Keep disabled for strict stability
};

Step 3: Configure Automatic Reboots & Maintenance Windows

When kernel patches or critical shared libraries (like glibc or OpenSSL) are updated, the server requires a reboot to load the patched code into memory. You can automate reboots during low-traffic hours: 

// Enable automatic reboot if /var/run/reboot-required exists
Unattended-Upgrade::Automatic-Reboot "true";

// Set reboot time to 03:30 AM server time
Unattended-Upgrade::Automatic-Reboot-Time "03:30";

// Reboot even if users are logged in via active SSH sessions
Unattended-Upgrade::Automatic-Reboot-WithUsers "true";

Step 4: Dry-Run and Verify Configuration

Always verify your syntax and dry-run the updater before leaving it to run automatically:

# Run in debug mode without applying changes
sudo unattended-upgrades --dry-run --debug

Inspect the output. If valid, you will see package evaluations and log entries written to /var/log/unattended-upgrades/unattended-upgrades.log.

Frequently Asked Questions

Does unattended-upgrades reboot the server automatically?

By default, unattended-upgrades will NOT reboot your server even if a kernel patch requires it. You can configure Unattended-Upgrade::Automatic-Reboot "true"; and specify an exact time window (e.g., 03:00 AM) in /etc/apt/apt.conf.d/50unattended-upgrades.

Can automatic updates break production web applications?

When configured properly to apply only security patches (Ubuntu-security pocket), the risk is minimal because library APIs remain stable. Never enable automatic upgrades for non-security or third-party repositories without rigorous staging.

How do I test unattended-upgrades without waiting for cron?

Run sudo unattended-upgrades --dry-run --debug. This will evaluate all upgradable packages, verify security origins, and print simulated package installations without making changes.
