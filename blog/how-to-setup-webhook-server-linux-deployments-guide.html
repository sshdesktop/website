How to Set Up a Webhook Server for Linux Deployments (2026 Guide)

Setting up full-blown continuous deployment pipelines with Jenkins, GitHub Actions Self-Hosted Runners, or GitLab CI can consume gigabytes of memory and introduce unnecessary maintenance overhead on small-to-medium VPS servers. A lightweight webhook daemon listens for push events, validates cryptographic signatures, and pulls new code in seconds. Learn how to set up an enterprise-grade deployment webhook server on Linux in 2026.

How Webhook Deployments Work

When you push code to GitHub or GitLab, the repository provider sends an HTTP POST request containing event metadata and an X-Hub-Signature-256 header to your server. Your server verifies the cryptographic signature, matches the branch (e.g., refs/heads/main), and executes a deployment shell script.

Step 1: Install the Standalone Webhook Daemon

Install the fast, open-source webhook utility (written in Go):

# Ubuntu / Debian
sudo apt update
sudo apt install -y webhook

# Verify installation
webhook -version

Step 2: Create the Webhook Definition (hooks.json)

Create a secure directory and configuration file:

sudo mkdir -p /etc/webhook
sudo nano /etc/webhook/hooks.json

Paste the following production configuration with HMAC signature validation:

[
  {
    "id": "deploy-api",
    "execute-command": "/usr/local/bin/deploy-api.sh",
    "command-working-directory": "/var/www/api",
    "response-message": "Deployment triggered successfully",
    "trigger-rule": {
      "and": [
        {
          "match": {
            "type": "payload-hmac-sha256",
            "secret": "YourSuperSecretRandomWebhookToken123",
            "parameter": {
              "source": "header",
              "name": "X-Hub-Signature-256"
            }
          }
        },
        {
          "match": {
            "type": "value",
            "value": "refs/heads/main",
            "parameter": {
              "source": "payload",
              "name": "ref"
            }
          }
        }
      ]
    }
  }
]

Step 3: Create the Deployment Shell Script

Create /usr/local/bin/deploy-api.sh with error handling:

#!/usr/bin/env bash
set -euo pipefail

APP_DIR="/var/www/api"
echo "=== Deployment started at $(date) ===" >> /var/log/webhook_deploy.log

cd "$APP_DIR"
git pull origin main >> /var/log/webhook_deploy.log 2>&1
npm ci --production >> /var/log/webhook_deploy.log 2>&1
sudo systemctl restart api.service >> /var/log/webhook_deploy.log 2>&1

echo "=== Deployment finished successfully ===" >> /var/log/webhook_deploy.log
sudo chmod +x /usr/local/bin/deploy-api.sh

Step 4: Configure Systemd Service and Nginx Reverse Proxy

Create a systemd service file at /etc/systemd/system/webhook.service:

[Unit]
Description=Lightweight Webhook Deployment Daemon
After=network.target

[Service]
Type=simple
User=deployer
Group=deployer
ExecStart=/usr/bin/webhook -nopanic -hooks /etc/webhook/hooks.json -ip 127.0.0.1 -port 9000
Restart=always

[Install]
WantedBy=multi-user.target

Enable and start the service:

sudo systemctl daemon-reload
sudo systemctl enable --now webhook

Proxy webhook traffic through Nginx with SSL:

location /hooks/ {
    proxy_pass http://127.0.0.1:9000/hooks/;
    include proxy_params;
}

Step 5: Add Webhook to GitHub/GitLab

In your GitHub repository settings, navigate to Webhooks > Add webhook:

  • Payload URL: https://api.example.com/hooks/deploy-api
  • Content type: application/json
  • Secret: YourSuperSecretRandomWebhookToken123
  • Events: Just the push event.

Frequently Asked Questions

Why should I use a lightweight webhook daemon instead of heavy CI runners?

For small projects, staging servers, and independent VPS instances, running GitLab Runner or Jenkins consumes 500MB–2GB of precious RAM. A standalone Go webhook listener uses less than 15MB of RAM, starts instantly, and executes shell scripts directly on git push events.

How does HMAC SHA-256 secret verification prevent unauthorized deployment triggers?

GitHub and GitLab hash the webhook payload using a shared secret key and send it in the X-Hub-Signature-256 header. The webhook listener computes the identical hash locally; if the signatures mismatch, the request is rejected with HTTP 403, preventing attackers from triggering arbitrary builds.

Should the webhook listener run as the root user?

Never. Always create a dedicated unprivileged user (e.g., deployer) for the webhook daemon. Grant specific sudo privileges only for commands that require it (e.g., sudo systemctl reload nginx) in /etc/sudoers.d/deployer.
