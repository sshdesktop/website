OpenSSH Server Hardening: 10 Critical Security Steps (2026 Checklist)

Server Hardening By SSH Desktop Engineering Team • Updated November 2026 • 10 min read

OpenSSH is the most widely used remote management daemon on earth. However, out-of-the-box default configurations on many Linux distributions still permit password authentication, allow root login attempts, and accept legacy cryptographic algorithms. Securing your SSH daemon is the foundation of Linux server security.

Executive Summary

Hardening OpenSSH takes less than 10 minutes. By applying strict rules in /etc/ssh/sshd_config, you can eliminate password brute-force vulnerabilities, enforce modern Ed25519 keys, and close unused forwarding channels without compromising administrator workflow.

1. The 10-Step OpenSSH Hardening Checklist

Step 1: Disable Root Login

Direct root login is the prime target for dictionary bots. Force administrators to log in as an unprivileged user and escalate with sudo: 

PermitRootLogin no

Step 2: Disable Password Authentication Completely

Require public key authentication exclusively: 

PasswordAuthentication no
PubkeyAuthentication yes
PermitEmptyPasswords no

Step 3: Restrict Permitted Users & Groups

Explicitly define which accounts are allowed to establish SSH sessions: 

AllowUsers deploy adminuser
# or restrict by group:
# AllowGroups sshusers

Step 4: Configure Session Idle Timeouts

Disconnect inactive SSH terminal sessions automatically after 15 minutes: 

ClientAliveInterval 300
ClientAliveCountMax 3

Step 5: Limit Authentication Retries

MaxAuthTries 3

Step 6: Enforce Modern Ciphers & Key Exchange Algorithms

Deprecate older SHA-1, CBC, and 3DES algorithms by declaring modern cryptographic suites: 

KexAlgorithms curve25519-sha256,curve25519-sha256@libssh.org,diffie-hellman-group16-sha512
Ciphers chacha20-poly1305@openssh.com,aes256-gcm@openssh.com
MACs hmac-sha2-512-etm@openssh.com

Step 7: Disable X11 Forwarding If Not Needed

X11Forwarding no

Step 8: Disable Host-Based Authentication

HostbasedAuthentication no
IgnoreRhosts yes

Step 9: Change the Default Port (Optional Security Through Obscurity)

While not a substitute for key-based auth, changing port 22 to a high port (e.g. 2222 or 49152) cuts background bot scanner log noise by 95%: 

Port 2222

Step 10: Display a Legal Login Banner

Banner /etc/issue.net

2. Safe Deployment: How to Verify & Reload Without Lockout

Golden Rule of SSH Configuration

Never close your active SSH terminal connection until you have tested your new configuration in a second, independent session! 

# Step 1: Validate sshd_config syntax (must output zero errors)
sudo sshd -t

# Step 2: Reload the SSH daemon gracefully (does NOT terminate active connections)
sudo systemctl reload ssh   # On Ubuntu/Debian
sudo systemctl reload sshd  # On RHEL/CentOS

# Step 3: Open a second terminal and verify you can log in with your SSH key!

3. Frequently Asked Questions

How do I safely test my sshd_config changes without locking myself out?

Before reloading the SSH daemon, run sudo sshd -t to validate configuration syntax. Then reload with sudo systemctl reload ssh. Crucially, KEEP YOUR CURRENT SSH SESSION OPEN and open a new terminal window to test logging in. If the new connection fails, you can immediately fix the configuration from your active session.

Why is PasswordAuthentication no better than PermitEmptyPasswords no?

Setting PasswordAuthentication no completely turns off interactive password logins across the server, forcing every connection to authenticate via cryptographic keys (such as Ed25519). This neutralizes all automated dictionary and brute-force botnets instantly.

Which cryptographic key type should I standardize on in 2026?

Standardize on Ed25519 (ssh-keygen -t ed25519). It provides superior security margins compared to RSA, is immune to timing attacks, and features compact 68-character public keys that are fast to compute.
