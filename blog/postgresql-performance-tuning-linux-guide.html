PostgreSQL Performance Tuning on Linux: 10 Critical Optimizations (2026)

Database Performance By SSH Desktop Engineering Team • Updated November 2026 • 10 min read

PostgreSQL is renowned for data integrity and feature richness. However, default installations ship with configuration values dating back to hardware standards from the early 2000s—often allocating a meager 128 MB of RAM to shared buffers. In modern production environments with SSD storage and multi-gigabyte memory banks, tuning postgresql.conf can yield a 5x to 20x improvement in query execution speeds.

Executive Summary

PostgreSQL tuning centers on balancing memory allocations (shared_buffers, work_mem, effective_cache_size) with write-ahead log (WAL) checkpoint thresholds and autovacuum aggression. In this guide, we provide concrete calculation formulas for 8 GB, 16 GB, and 32 GB RAM servers alongside visual database management via SSH Desktop Database GUI.

1. Memory Allocation Formulas

1. shared_buffers (Dedicated Cache)

Sets the amount of memory PostgreSQL uses for shared memory buffers. Recommended setting: 25% of total server RAM. 

# 8GB RAM Server:
shared_buffers = 2GB

# 16GB RAM Server:
shared_buffers = 4GB

# 32GB RAM Server:
shared_buffers = 8GB

2. effective_cache_size (Planner Memory Estimate)

Provides an estimate of memory available for disk caching by both PostgreSQL and the OS kernel. Recommended: 50% to 75% of total server RAM. 

effective_cache_size = 12GB  # For 16GB RAM server

3. work_mem (Per-Operation Sort Memory)

Used for internal sort operations and hash tables before writing to temporary disk files. 

# Formula: (Total RAM - shared_buffers) / (max_connections * 3)
work_mem = 32MB

4. maintenance_work_mem

Specifies the maximum amount of memory to be used by maintenance operations like VACUUM, CREATE INDEX, and ALTER TABLE: 

maintenance_work_mem = 1GB

2. Write-Ahead Log (WAL) & Checkpoint Tuning

Aggressive checkpointing causes sudden I/O spikes that stall queries. Smoothing checkpoint execution avoids disk thrashing: 

# Spread out checkpoints across 90% of the checkpoint interval
checkpoint_completion_target = 0.9

# Increase maximum WAL volume between automatic checkpoints
max_wal_size = 16GB
min_wal_size = 2GB

# Tune random page cost for modern NVMe/SSD storage (Default 4.0 is for spinning rust!)
random_page_cost = 1.1

3. Autovacuum Tuning: Preventing Table Bloat

PostgreSQL uses Multi-Version Concurrency Control (MVCC). Dead row versions must be vacuumed frequently to maintain index density: 

autovacuum = on
autovacuum_max_workers = 4
autovacuum_vacuum_scale_factor = 0.05
autovacuum_analyze_scale_factor = 0.02

4. Frequently Asked Questions

Why is the default postgresql.conf so conservative?

The default PostgreSQL configuration is deliberately designed to run on virtually any hardware—including minimal 512 MB embedded devices—without failing to start. In production servers with 8 GB to 64+ GB of RAM, running default settings leaves over 90% of available memory unutilized.

What percentage of RAM should be assigned to shared_buffers?

On dedicated Linux database servers, standard practice is to allocate 25% of total physical RAM to shared_buffers. Allocating more than 40% usually leads to diminishing returns and double-buffering contention with the Linux kernel page cache.

What is the danger of setting work_mem too high?

Unlike shared_buffers which is allocated once at startup, work_mem is allocated PER SORT AND HASH OPERATION per active connection. If you set work_mem = 256MB with max_connections = 100, a complex query involving multiple join sorts can exhaust physical RAM and trigger the Linux OOM Killer.
